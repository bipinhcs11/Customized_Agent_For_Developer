# FeatureBased Skill Generator Agent

## What this is

A customizable AI agent that reads any Java repository — Spring Boot, Spring MVC, Struts, Quarkus, Spring Batch, Quartz, raw servlets, or any mixed/legacy combination — automatically identifies its business features, and writes one rich `SKILL.md` file per feature into `.github/skills/<feature-id>/`. Those skill files become the persistent, AI-readable context that GitHub Copilot and Claude consume on every subsequent question, so neither has to rediscover the domain from scratch and the developer never has to retype "this is the FileDelivery feature, the DB table is X, the status enum is Y..." again.

Once skills exist, they are kept current automatically by a Phase-2 updater that re-runs the relevant slice of the pipeline when code changes (PR merge, git hook, file watch, or manual CLI command).

---

## Why this exists

Enterprise developers typically have a small monthly Copilot premium-request budget (around 300 requests/month). Without persistent feature context, every premium request burns tokens re-explaining the same domain — and the answer is still often wrong because the AI is guessing. With persistent skills:

- Copilot and Claude start each conversation already knowing the feature
- Answers are accurate because they are grounded in the actual code
- No back-and-forth — the right answer comes first time
- A single enterprise repo can have 50–200 features; this scales

The skill files are the contract; the AI is the consumer; the developer stops being the human RAG layer.

**Execution model: host-agent-driven.** The Python tool is deterministic and stdlib-only — it never makes outbound API calls. Every LLM-dependent stage emits a prompt file; the developer pastes it into their existing AI session (Claude Code, Codex, Copilot Chat, Cowork); the response is saved back to a file; the tool ingests it. No API keys, no extra cost lines.

## Packaging — two equivalent forms

The agent is delivered in two forms that share the same prompt strings, so behaviour is identical regardless of how it is invoked:

| Form | Location | Run from | Best for |
|---|---|---|---|
| Claude skill | `skills/skill-generator/SKILL.md` | Copilot Chat, Claude Code, Cowork | Interactive use, exploring a new repo, one-off runs |
| Python CLI | `tools/skill_generator/` | Terminal, CI, GitHub Action | Deterministic runs, large repos needing rate limiting and checkpointing, automation |

Both read the same configuration and produce identical output.

## Phase 1 — The four-stage generation pipeline

### Stage 1 — Crawl (zero LLM turns)

Walks the target repo locally and builds an index JSON of every relevant file. This stage spends zero tokens. It reads:

- `*.java` — package name, class name, type (class / interface / enum / record), annotations (first 5), method names (first 10), `extends` / `implements`, import tail tokens, line count, and flags (`deprecated`, `god_class`, `test`, `generated`)
- `web.xml` — servlet class names and URL patterns
- `struts-config.xml` — action paths and action class names
- `applicationContext*.xml` and other Spring XML — bean ids and class attributes
- `hibernate.cfg.xml` and `*.hbm.xml` — mapped class names and table names
- `persistence.xml` — JPA entity class names
- `quartz*.xml` — job class names and cron expressions
- `*.properties`, `*.yml`, `*.yaml` — key prefixes such as `datasource.*`, `mail.*`, `file.*`, `batch.*`, `queue.*`, `scheduler.*`

It skips silently: `target/`, `build/`, `.git/`, `generated/`, `.mvn/`, binary files (`.class`, `.jar`, `.war`, `.ear`), empty files, and files marked `// DO NOT EDIT`, `@Generated`, or `// generated by`.

### Stage 2 — Plan (one host-agent turn)

`plan-emit` writes a prompt containing the slimmed index JSON and the grouping rules. The developer pastes that prompt into their AI session and saves the response. `plan-ingest` parses the response into `plan.json`.

Grouping rules used in the prompt:

- Primary signal: package name
- Secondary signal: class name prefix (e.g., `FileDelivery*`, `SeedData*`, `Search*`)
- Tertiary signal: annotations and XML mappings
- God classes flagged at Stage 1 are split by method-name cohesion groups, each becoming its own domain entry with `isGodClassSplit: true`
- Deprecated classes are included and flagged
- Generated classes are excluded entirely
- Shared utilities used by 3 or more domains are assigned to a `shared-infrastructure` domain
- Spring XML beans are assigned to the same domain as the Java class they reference
- Struts actions are assigned to the domain of the service they call
- Batch Jobs and Steps become one domain per distinct Job if the business logic differs
- Default-package classes are grouped by their longest common class-name prefix

Output: a JSON document containing `projectType`, `framework`, `buildSystem`, `javaVersion`, `warnings[]`, and a `domains[]` array where each domain has an `id`, `name`, `description`, `classes[]`, `xmlSources[]`, `configKeys[]`, `confidence`, `isGodClassSplit`, `godClassParent`, `flags[]`, and `estimatedTokens`.

The plan is shown to the developer in the IDE panel. The developer can toggle domains on or off, merge two domains, or rename a domain. The pipeline does not proceed until the developer confirms.

### Stage 3 — Generate (one host-agent turn per approved domain)

`generate-emit` writes one prompt per domain to `.skill-gen/.generate-prompts/<domain-id>.md`. Each prompt contains:

1. The full source of all files whose classes belong to this domain
2. Relevant XML excerpts (bean definitions only, comments stripped)
3. Relevant config key-value pairs
4. The Stage-3 prompt template (frontmatter contract, body section rules, citation rules)

If total characters exceed `max_chars_per_chunk` (default 24,000), the source is truncated with a marker noting the overflow — splitting a domain across multiple turns is on the roadmap.

The developer pastes each prompt into their AI session and saves each response as `.skill-gen/.generate-responses/<domain-id>.md`. `generate-ingest` reads each response and writes `<output-dir>/<domain-id>/SKILL.md`.

Output: one `.github/skills/<domain-id>/SKILL.md` per domain, conforming to the artifact-3 standard.

### Stage 4 — Link (one host-agent turn)

`link-emit` collects the first ~600 characters of each generated SKILL.md plus its domain id and writes a prompt asking the host agent to identify cross-domain dependencies. Signals: direct class instantiation across domains, injected services from another domain, shared DAOs, exceptions thrown in one domain caught in another, config values shared across domains.

The host agent's response is a JSON `links[]` array where each link has `from`, `to`, `reason`, and `type` (`calls` / `shares` / `extends` / `configures`). `link-ingest` reads that response and, for each link, updates **both** SKILL.md files: writes `related_skills` in the frontmatter and adds a row to the Related Skills table in the body.

On the `to`-side SKILL.md, the relationship type is written in its inverted form so the direction stays clear when reading either skill in isolation:

| Forward (`from` side) | Reverse (`to` side) |
|---|---|
| `calls` | `called-by` |
| `extends` | `extended-by` |
| `configures` | `configured-by` |
| `shares` | `shares` (symmetric) |

**Total host-agent turns for a 10-domain repo:** approximately 12 (1 plan + 10 generate + 1 link). All inside an AI session the developer already has — no extra subscription, no API key.

## Phase 2 — The updater (keeps skills current)

When code changes, the agent re-emits prompts only for the affected slice of the pipeline.

| Trigger | Mechanism | When to use |
|---|---|---|
| Manual CLI | `skill-gen update-emit --feature file-delivery`, paste into AI session, `skill-gen update-ingest --commit` | One-off corrections; default workflow |
| Local script | Wraps both halves around your AI tool's CLI (if scriptable) | Power users automating against Claude Code CLI / Codex CLI |

(A GitHub Action variant requires either (a) a future API-call-enabled mode, or (b) an automation-friendly host agent surface. Both are out-of-scope for v0.3.)

The updater workflow:

1. `update-emit` receives the list of changed files from `git diff`
2. Maps file paths to feature ids using existing skill folders
3. Re-reads only the affected features' source
4. Writes one prompt per affected feature to `.skill-gen/.update-prompts/<feature-id>.md`
5. Developer pastes each prompt into their AI session, saves response
6. `update-ingest` reads each response, increments `version`, sets `last_updated` to today's date
7. With `--commit`: commits with message `chore: update <feature> skill (auto)`

The updater never re-emits the Plan stage unless a brand-new feature appears (new package, new Struts action, new Quartz job).

## The SKILL.md standard

Every generated and authored SKILL.md conforms to the artifact-3 standard:

- Lives at `.github/skills/<domain-id>/SKILL.md` in target repos (or `skills/<feature>/SKILL.md` for the reference skills in this repo)
- Starts with required frontmatter: `skill`, `domain`, `version`, `project_type`, `framework`, `java_version`, `legacy`, `status`, `flags`, `related_skills`, `generated_by`, `last_updated`
- Has these body sections in this exact order: Purpose, Entry Points, Business Logic (Core Flow + Validation Rules + Business Rules), Key Classes & Files, Data Flow, Database & Storage, External Dependencies, Error Handling, Edge Cases, Legacy Notes, Related Skills, AI Agent Instructions
- Contains no Java code snippets in the body — table rows and cited rules only
- Cites `ClassName.methodName()` for every entry point, validation rule, business rule, and edge case
- Writes the literal string `none found` rather than omitting a section
- Increments `version` by 1 on every update (integer, not semver)

Full spec: https://claude.ai/public/artifacts/1689b220-c09f-467c-a8af-1eb3bb1a30fe

## Enterprise multi-repo support

A central `agent-config.yml` lists all repositories the agent maintains across an enterprise:

```yaml
repos:
  - name: payment-service
    path: /enterprise/payment-service
    features:
      - file-delivery
      - payment-method-determination
  - name: finance-service
    path: /enterprise/finance-service
    features:
      - invoice-compare
```

Multi-repo orchestration is on the roadmap. The intended UX: a wrapper script reads `agent-config.yml` and runs the emit/ingest cycle per repo, prompting the developer through each AI session turn. Each target repo ends up with its own `.github/skills/` directory.

## Supported Java flavors

The Stage 1 crawler and Stage 2 planner recognise and adapt to:

- Spring Boot 2.x / 3.x (annotation-driven REST + Spring Data JPA)
- Spring MVC (XML or annotation configuration)
- Struts 1 and Struts 2 (XML action mappings)
- Quarkus (JAX-RS annotations)
- Spring Batch (Job / Step / Processor)
- Quartz Scheduler (cron-driven jobs)
- Raw servlets (web.xml URL patterns)
- Mixed legacy repos (multiple of the above in one codebase — the planner picks the dominant signal per domain)

The generated SKILL.md accurately describes whatever the target repo actually uses. It does not impose Spring Boot conventions on a Struts codebase.

## Configuration

There is no `model:` setting — the model is whichever one your host AI session is running. For enterprise guidance on when to use Claude Opus-class sessions, Claude Sonnet-class sessions, Codex, or Copilot Chat from VS Code/IntelliJ, see `docs/enterprise-agent-selection-guide.md`. Override paths via CLI flags:

| Flag | Default | What it does |
|---|---|---|
| `--output-dir` | `<repo>/.github/skills/` | Where SKILL.md files land (generate-ingest) |
| `--prompts-dir` | `<repo>/.skill-gen/.generate-prompts/` | Where per-domain prompts are written |
| `--responses-dir` | `<repo>/.skill-gen/.generate-responses/` | Where to look for per-domain responses |
| `--exclude` | (see `crawler.py`) | Additional directories to skip in crawl |
| `--skip-tests` | off | Exclude `*Test.java` and `/test/` paths |
| `--force` | off | Overwrite an existing SKILL.md on ingest |
| `--only DOMAIN_ID` | (all) | Restrict emit/ingest to one domain |
| `--commit` | off | (update-ingest) git-add + commit the refreshed SKILL.mds |

The crawler-internal constants (god-class threshold, chunk cap, exclude paths) live in `tools/skill_generator/crawler.py` and `generate.py`.

## Edge cases the agent handles

| Scenario | Handling |
|---|---|
| God class > 300 lines | Planner splits by method group; each split is its own domain with `isGodClassSplit: true` |
| Domain source > 24KB cap | Truncated with marker; split-and-merge across multiple turns is roadmap |
| Default-package classes | Group by longest common class-name prefix |
| XML-only wiring (no annotations) | XML signals drive domain assignment |
| Deprecated class | Included, flagged in `Legacy Notes` and frontmatter `status: deprecated` |
| Generated code (`@Generated`, `// DO NOT EDIT`) | Skipped at crawl stage |
| Crash mid-run | Re-run the last emit/ingest — outputs are idempotent; ingest skips existing SKILL.md unless `--force` |
| Existing SKILL.md present | `generate-ingest` skips it unless `--force` is passed |
| Zero Java files found | Exit with error message to developer |

## Constraints

- The agent produces `SKILL.md` files only — it does not generate Java code
- Generated skills must describe the target repo's actual conventions, not the reference conventions used in `examples/`
- Skills must be self-contained — reading one SKILL.md gives full feature context with zero additional file reads required
- The agent itself is usable from GitHub Copilot Chat, Claude Code CLI, and Claude Cowork, by virtue of being packaged as both a Claude skill and a Python CLI
- Do not use Lombok in the reference Java examples unless explicitly asked
- Do not add Spring Security configuration to the reference Java examples unless asked
- The reference Java examples use PostgreSQL by default and Java 17+, but generated SKILL.mds describe whatever stack the target repo runs
